# 考研互相督促学习板（SETI）设计文档

- 日期：2026-08-31
- 状态：待用户审阅
- 类型：新项目（Architectural）

## 1. 背景与目标

用户与 2-5 位熟人朋友共同备战考研，需要一个互相督促的网站。核心诉求不是陌生人社交，而是**熟人间的"互相看见 + 轻压力"**。

网络调研关键结论（2026-08）：

- 新华网报道的调查显示 73.91% 的人认为纯打卡督促作用不大，80% 的人打卡撑不过 50 天 → **纯打卡必死，必须做"互见 + 轻压力 + 通知闭环"**
- CoStudy/Timing 等虚拟自习室的陌生人社交氛围被媒体批评"冲淡学习气氛"，与本项目熟人场景错位
- Focusmate 验证的 body doubling（同伴在场感）机制有效，但视频形式压力过大
- 契约 + 明确奖惩 + 严格执行是最有效的监督机制

**成功标准**：朋友们连续 4 周保持每日打卡率 > 70%，且产品迭代由真实使用反馈驱动。

## 2. 产品设计

### 2.1 形态

响应式 Web 应用（手机优先），房间码制的熟人小圈子，共 5 个核心页面。

### 2.2 打卡规则（已确认）

| 规则 | 决策 |
|------|------|
| 粒度 | 一天多次，分科目记录；当日提交任意一条即算"今日已打卡" |
| 有效性 | 照片可选；无照片的打卡标记"无凭证"，体现在热力图与周报 |
| 截止 | 次日 01:00（北京时间）截止，过期锁定，**不可补卡** |
| 凌晨归属 | 00:00–01:00 打开打卡页：默认日期 = **昨天**（夜车补记录场景），可手动切为"今天"；01:00 后昨天的永久锁定 |
| 科目删除 | 科目有历史打卡记录时**禁止删除**（防止统计断裂），只能改名/排序；无记录的可删 |
| 时长 | 纯手动填写分钟数 |
| 科目 | 预置"政治/英语/数学/专业课"模板 + 每人自定义（改名/增删） |
| 照片 | 1-3 张，前端压缩后上传，仅登录圈内成员可见 |

### 2.3 督促闭环（已确认）

```
21:00   当日未打卡者 → Server酱微信提醒「今天还没打卡」
随时    朋友点「催一下」→ Server酱推送「XX 催你学习」（每人每天对同一人限 1 次）
01:00   次日截止 → 日期锁定，未打卡显示「缺卡」，永久不可补
每周一  生成上周结算 → 周结算页 + Server酱周报摘要
```

### 2.4 页面清单

| 路由 | 内容 |
|------|------|
| `/login` `/register` | 用户名密码登录；凭邀请码注册（无邀请码无法注册） |
| `/` 今日动态流（核心页） | 顶栏：考研倒计时 + 全员今日状态角标；正文：打卡卡片流（无凭证标记、点赞、评论）；未打卡者置底灰色卡片 + 「催一下」按钮 |
| `/checkin/new` | 选科目 → 填时长 → 一句话总结 → 照片可选 |
| `/me` | GitHub 风格热力图、连续天数、累计时长、按科目统计 |
| `/weekly` | 上周排行：打卡天数 / 总时长 / 无凭证次数；缺卡最多者高亮 |
| `/settings` | Server酱 SendKey、科目管理、昵称头像 |
| `/admin`（首个注册者） | 考研日期、截止/提醒时间、邀请码重置、手动「立即提醒」按钮 |

### 2.5 角色与安全

- 第一个注册用户自动成为管理员（`is_admin`）
- **管理员可重置任意成员密码**（无邮箱体系下丢密码的唯一恢复路径）
- 密码 bcrypt 哈希存储；会话用加密 Cookie
- 允许多设备同时在线
- 所有照片接口鉴权后流式返回，不暴露静态目录

### 2.6 已知限制（一期接受）

- Server酱免费版每人每日 5 条推送上限：21:00 提醒 1 条 + 催学若干 + 周报 1 条，极端情况会触顶；超发推送静默失败（记日志），不影响站内显示
- 3 Mbps 带宽下多图加载稍慢；靠前端压缩（单张 ≤ 300KB 目标）缓解

## 3. 技术架构

### 3.1 技术栈（已确认）

| 层 | 选择 |
|----|------|
| 框架 | Next.js 15 + App Router + React 19 + TypeScript |
| 样式 | Tailwind CSS 4 + shadcn/ui |
| ORM | Prisma + SQLite |
| 认证 | iron-session（加密 Cookie 会话） |
| 推送 | Server酱（`sctapi.ftqq.com/{key}.send`），失败仅记日志不阻塞主流程 |
| 定时 | 服务器 crontab 调带密钥的内部 API + 管理员手动按钮兜底 |
| 测试 | Vitest（纯函数 TDD 先行 + API 权限测试） |

### 3.2 数据模型

```
User     id, username(unique), password_hash, display_name,
         serverchan_key?, is_admin, created_at

Subject  id, user_id, name, sort_order          // 每人自己的科目列表

CheckIn  id, user_id, subject_id, date,         // date = 北京时间 YYYY-MM-DD
         duration_minutes, note, has_photo, created_at

Photo    id, checkin_id, file_path, created_at

Comment  id, checkin_id, user_id, content, created_at

Like     (checkin_id, user_id) 联合主键

Nudge    id, from_user_id, to_user_id, date
         UNIQUE(from, to, date)                 // 每天每人只能催同一人一次

Setting  key, value                             // exam_date / deadline_hour /
                                               // remind_hour / invite_code / cron_secret
```

### 3.3 关键实现约束

1. **时区收口**：所有日期/跨天/streak/周结算计算集中到 `lib/dates.ts` 纯函数，统一 `Asia/Shanghai`，全站唯一入口。
2. **截止不依赖定时任务**：某日期能否打卡由「当前北京时间 vs 该日期截止点」实时计算，cron 只负责提醒，不做数据锁定，避免 cron 故障导致状态错乱。
3. **照片上传**：API 路由校验类型与大小，落盘到数据目录；返回时鉴权 + 流式输出。
4. **Nudge 幂等**：数据库唯一约束兜底，接口层捕获冲突返回友好提示。

## 4. 部署方案（依据服务器截图定稿）

### 4.1 服务器环境（阿里云 ECS 截图确认，2026-08-31）

| 项目 | 值 | 影响 |
|------|-----|------|
| 系统 | Alibaba Cloud Linux 3.2104 LTS（RHEL 兼容，dnf） | Node.js 走 NodeSource/阿里镜像源 |
| 规格 | 2 vCPU / 2 GiB / 40 GiB ESSD | **内存是硬约束 → 放弃 Docker 和宝塔，PM2 直跑最省** |
| 带宽 | 3 Mbps 固定 | 照片必须前端压缩（已定），单张控制在 ~300KB |
| 公网 IP | 123.56.223.97 | 未备案域名暂不走 80/443 绑域名，先 `IP:端口` |
| 到期 | 2027-05-02 | 覆盖初试（2026-12）+ 复试（2027-03/04）全周期 ✅ |
| 现状 | 全新服务器，已装扩展数 0 | 无历史环境冲突，干净起步 |

### 4.2 部署架构

```
用户浏览器 → http://123.56.223.97:8080 → Caddy（反向代理）
                                          → localhost:3000 PM2 守护的 Next.js
                                          → SQLite 文件 + 照片目录（同一数据盘目录）

crontab: 21:00 提醒 API ｜ 每日 03:00 备份（SQLite + 照片，保留 7 份）
```

- **进程管理**：PM2 + `pm2 startup` 开机自启 + `pm2 save`
- **反向代理**：Caddy（配置极简；域名备案后加 3 行即自动 HTTPS）
- **访问入口**：`http://123.56.223.97:8080`（阿里云安全组需放行该端口）
- **注意**：截图显示云监控插件"安装失败"——不影响本项目，可忽略

### 4.3 部署执行方式

- **构建发生在开发机（Windows 本地），服务器只跑产物**：2G 内存服务器上执行 `next build` 可能 OOM，因此本地构建后上传 `.next` + 依赖，服务器只执行 `next start`
- 部署脚本为服务器**加 2G swap 兜底**，防运行期内存尖峰
- PM2 环境变量固定 `TZ=Asia/Shanghai`；`lib/dates.ts` 统一用本地时间函数，禁止混用 UTC getter
- 由 Claude 通过 SSH 代为部署；用户届时提供**临时专用密码**，验收完成后自行修改
- 交付 `deploy/` 目录：`setup.sh`（装 Node/PM2/Caddy/swap）、`deploy.sh`（上传产物并重启）、`rollback.sh`
- 部署后按手动验收清单逐项验证

## 5. 测试策略

- **Vitest 单测（TDD 先行）**：`lib/dates.ts` 全部边界（23:59/00:30/01:00、周一跨界、闰月）、streak 断续计算、周结算归属
- **API 测试**：权限（不能删改他人记录、未登录不可见照片/数据）、Nudge 重复、邀请码错误
- 不做 E2E；部署后执行手动验收清单

## 6. 一期不做（YAGNI）

- 实时状态灯 / 共享番茄钟（二期候选）
- 奶茶债等债务记账（线下自记）
- 邮件通知降级通道（Server酱够用，需要时再加）
- 多房间 / 陌生人开放注册
- 原生 App / 小程序
- 打卡内容编辑与删除以外的复杂审核流
